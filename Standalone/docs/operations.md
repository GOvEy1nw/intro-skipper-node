# Operations

## Windows tray app

This repository publishes source only; it includes no desktop package, model weights or bundled tools. A private all-in-one `IntroSkipper-Node.exe` requires the builder to supply the .NET Windows/ASP.NET runtime, CPython with the pinned NumPy/OpenCV packages, FFmpeg, FFprobe, inference helper, model manifest and weights. GPU options use the installed graphics driver.

Double-click the EXE. It opens the connection page and stays in the Windows notification area. A configured node with a saved/environment credential starts automatically; otherwise enter its name, server address and API key and start it. Configure libraries and scanning options in Intro Skipper's **Nodes** tab. The tray and page control one worker. Grey means stopped, amber starting/disconnected/server-disabled, green connected and waiting, blue scanning, and red an error. **Open web UI**, **Start node**, **Stop node** and **Quit** share the same lifecycle. Closing the browser leaves the node running; Quit cancels and drains its helpers.

The default settings file remains `%LOCALAPPDATA%\SegmentScanner\worker.json` for upgrade compatibility. A private build can seed node identity and state/cache references; it contains no key, credential file, database, reports or media. Use `IntroSkipper-Node.exe --config FILE` for another configuration. Builder-supplied tools overlay paths in memory; saved credentials and results keep their existing locations. Logs are beside the selected config under `logs\desktop.log`, with one previous log retained after 5 MiB.

The single-file .NET host extracts tools into its versioned per-user cache (normally `%TEMP%\.net`). Upgrades use a new runtime cache while reusing persistent configuration and state. Do not remove the active runtime cache while the app is running. If temporary files were cleaned or extraction was interrupted, close the app and launch the complete EXE again. `DOTNET_BUNDLE_EXTRACT_BASE_DIR` can select a different extraction location before launching. No runtime cache cleanup or Windows startup registration is performed by the app.

Build locally from builder-supplied inputs with `Standalone/packaging/windows/build-desktop.py --python VENV_PYTHON --ffmpeg FFMPEG --ffprobe FFPROBE --model-manifest MANIFEST --output OUTPUT_ROOT [--seed-config CONFIG]`. The script uses the pinned local Python packages and supplied model, checks dependency imports and model SHA-256, starts the bundled inference helper against that model, includes third-party notices, and produces a self-contained Windows x64 EXE. No model is downloaded. The output includes a receipt outside the single-EXE delivery folder.

Automatic imports are a server-owned node option, off for new policies. Enable **Use complete scan results automatically** in Intro Skipper → **Nodes** and save. It is pinned with scope, method, recipe and revision; calibration status stays unchanged. Complete recognized results use normal server admission and projection. Failed, incomplete, censored, invalid-offset or unknown evidence cannot overwrite markers automatically. Earlier held proposals stay held; fresh work uses the changed policy.

Clear that checkbox and save to stop future automatic imports, or disable the node to prevent new work. Policy changes invalidate old jobs and reschedule pending targets with fresh snapshots. Already imported markers remain editable. Keep matching bridge/worker binaries and a consistent database backup for rollback.

## Command-line and web settings

`settings --config FILE` opens the minimal connection and Start/Stop page. It binds IPv4 loopback with a session token and host/origin checks. Windows remembers a successfully connected API key until **Remove remembered key** is used. Credentials and the DPAPI key ring remain in the state directory's `.segmentscanner-credentials` folder, bound to server URL and Windows account; keys are never returned to the page or stored in settings JSON. Environment credentials take precedence. Moving to another account/PC requires entering the key again. Other platforms support session and environment credentials. One process owns a state directory. The CLI retains `doctor`, `scan --manifest --modes intro,credits,recap,preview,commercial --dry-run --out`, `report`, `review`, `export`, `work`, `sync`, `evaluate` and `compare` for explicit operations.

Use `doctor` before a scan. It must confirm the configured FFmpeg, Python helper, model manifest, media roots, state/cache directories, and export destination. `scan --dry-run` may read media and write its requested local output, but must not mutate a server, media file, or adjacent sidecar. No command downloads a model at startup.

For normal connected credits scans, the bridge checks matching authored credits chapters before queuing remote work. A valid chapter settles the episode without running the standalone credits detector; unmatched episodes use scanning as the fallback. Explicit chapter enhancement and forced-analyzer actions retain their existing behavior. Upgrading this routing fix does not require clearing the worker cache.

The plugin's **Nodes** tab selects **Text-aware** or **Original Intro Skipper** credits. Text-aware uses the text model and frame-group rules. Original reuses the combined keyframe/card and shared-audio credits pass. This is separate from the deprecated black-only analyzer. Matching chapters take precedence under normal chapter policy; when local scanning is disabled, the worker handles that stage.

Save a method or GPU change in the plugin; the connected node receives a notification. Running jobs retain their snapshots and stale policy cannot import. **Use GPU** enables video decoding for Original and decoding plus OpenCL inference for Text-aware. CPU remains the default, resizing/colour conversion stay on CPU, and unsupported requested hardware fails clearly. Original needs no Python or model inference; its final comparison and storage remain serial. CPU and GPU recipes use separate cache/profile identities.

Original jobs pin the server's effective credits settings and retain scoped comparison-only siblings, including chapter-settled episodes. Their raw-evidence cache is separate from text-aware frame evidence. Automatic imports still require the node's explicit setting and the existing server admission checks. Original results with incomplete comparison inputs, unknown chapter dependencies or an unproved shorter-audio ending remain held; a negative result must cover the configured original ending window. Install the matching bridge and worker together before selecting this method.

`resources.ffmpegThreads` and `resources.inferenceThreads` accept 1–32 threads per process. The worker passes the inference limit to the Python helper, which calls OpenCV's thread control before loading the network. `doctor` reports the effective OpenCV count and configured limit. Older workers only set `OMP_NUM_THREADS`, which did not control the Windows Concurrency backend: a configuration saying two could actually use 32. With the corrected worker/helper pair, two really limits inference to two and may be slower. Update the helper path as well as the worker when upgrading. Choose counts from measurements; more threads can add overhead rather than throughput. Thread counts are diagnostic resource settings, not part of the semantic model/profile identity. The verified feature cache remains reusable.

**Parallel workers** in the plugin accepts 1, 2 or 4, defaulting to 2 for new remote nodes. It bounds intro fingerprint extraction and credits file pipelines; comparisons and result saving remain serial. Existing counts migrate once. Each text worker owns its detector and a share of temporary storage. Use 1 for lower CPU/GPU/NAS demand. The local node control bounds concurrent seasons.

Only one connected job and lease run at a time. Changing the worker count preserves detector profiles and reusable evidence. Evidence eviction waits until all credits workers have stopped; duplicate media share one worker to avoid overlapping cache writes. Do not launch multiple app processes against one state directory; the local store lock prevents that.

CPU remains the default. Connected nodes use the plugin's single **Use GPU** checkbox and an advertised recipe, preferring an initialized NVIDIA decoder over Intel when both are available. Text inference uses OpenCL FP32; no custom CUDA-enabled OpenCV, Vulkan or FP16 mode is needed. Offline CLI configurations still expose `credits.inferenceBackend` and `credits.videoDecoder` separately.

The decoder policy supports CPU, NVIDIA NVDEC and Windows Intel Quick Sync for H.264, HEVC and AV1 with 8-bit or 10-bit 4:2:0 input, subject to device codec support. Unsupported codecs, formats or unavailable requested hardware fail clearly. Choose CPU for unsupported files. HDR remains unsupported pending a calibrated tone-mapping profile.

AV1 analysis omits generated film grain from temporary thumbnails on every backend, including CPU. Applying that grain was the measured Intel bottleneck on the test files. The media itself is untouched. This v3 decoder policy changes the declared credits profile on every configuration and invalidates AV1 evidence, because image features can differ even when marker boundaries agree. Existing non-AV1 CPU evidence keeps its v2 cache identity. Hardware evidence keys also record the decoder, source codec and pixel format. Decoding and text detection are independent choices, so Intel decoding can feed NVIDIA OpenCL inference on a PC with both GPUs. Stop the worker, save and register the new profile, then queue fresh work after upgrading or changing either choice.

The CPU and Intel AV1 decoders export grain parameters instead of applying them. NVIDIA AV1 uses FFmpeg's native AV1 hardware decoder through NVDEC: the cuvid AV1 wrapper accepted the export flag but retained grain in the measured build, so it cannot implement this policy. H.264/HEVC NVIDIA decoding still uses cuvid. See [FFmpeg's grain side-data option](https://ffmpeg.org/ffmpeg-all.html#Codec-Options) and [Intel's film-grain setting](https://intel.github.io/libvpl/v2.10/API_ref/VPL_structs_cross_component.html).

`doctor` checks decoder availability and initializes the selected hardware device; actual per-file codec support is checked while scanning. Hardware video decoding runs through FFmpeg and the installed graphics driver, independently of OpenCV's text-detection backend. No extra OpenCV build is needed. See [FFmpeg hardware options](https://ffmpeg.org/ffmpeg-all.html#Advanced-Video-options). The Intel route was validated on Windows with the UHD 770 and uses Direct3D 11 through Quick Sync; Linux Intel decoding is not validated by this option.

Run `doctor` with that configuration. GPU mode requires an available OpenCL GPU and a successful actual OpenCL network forward; it reports the selected device, vendor and driver. Unsupported devices or CPU fallback fail clearly rather than quietly running CPU. The first run may spend extra time compiling GPU kernels. Results vary by device and driver: the default GPU on the tested Windows PC was the NVIDIA RTX 4070 Ti SUPER. GPU inference can produce small floating-point differences, so its profile and evidence-cache identity are separate from CPU; the cache also records the actual GPU and driver. Switching back selects the current CPU profile and reusable evidence for its decoder policy. Credits still require review, and changing this option does not rewrite accepted markers.

The existing Python environment supports both CPU and OpenCL without another package. Other OpenCV backends depend on build options and their own libraries; they are outside this worker's supported choices. See the [OpenCV build configuration](https://docs.opencv.org/4.13.0/db/d05/tutorial_config_reference.html).

Intro fingerprinting already selects only audio for FFmpeg's Chromaprint output. It does not decode the video stream, so hardware video decoding cannot accelerate this path. The current audio decoding, downmixing and Chromaprint computation remain CPU work; there is no corresponding GPU switch. See [FFmpeg Chromaprint output](https://ffmpeg.org/ffmpeg-all.html#chromaprint) and [Chromaprint's FFT backends](https://github.com/acoustid/chromaprint#fft-library). CPU fingerprint parallelism would need a separate throughput and resource-limit evaluation.

On Windows, publish the console package, then run `packaging/windows/Install-SegmentScanner.ps1` from an elevated PowerShell with an install directory and a state directory. It creates an at-startup Scheduled Task and copies `samples/config.windows.json` only when the configured state file does not already exist. The action quotes the config path for worker launch. Configure the task account to have read access to the media share and read/write access to state, cache, and the separate export directory. Use `Stop-SegmentScanner.ps1` to stop it; `Uninstall-SegmentScanner.ps1` only unregisters the task. Neither removes configuration, local state, accepted results, or sidecars. The script has parser coverage only; task registration and launch remain deployment checks.

For Linux, build the supplied Dockerfile from the repository root and use `compose.cpu.example.yml` as the mount template. It runs UID/GID `10001`, mounts `/media` read-only, and keeps state, cache, and exports in separate writable mounts. The Linux builder uses `10.0.401-noble` through `packaging/linux/global.json` because no Linux SDK `10.0.303` image is published; Windows remains pinned to root `global.json` `10.0.303`. Place the BYO model at repository-root `model_v1.pb`; the compose mount preserves the checked-in manifest's relative reference. An FFmpeg/FFprobe pair is also a BYO read-only mount; `upstream-lock.json` deliberately does not label its development FFmpeg reference as a packaged release. It publishes no ports and starts no worker HTTP service. If exports must sit beside media, replace the read-only media mount deliberately and use an export policy that protects media files; this is not enabled by the example.

Validate a Linux deployment with Linux-native FFmpeg and FFprobe mounted at `/tools/ffmpeg` and `/tools/ffprobe`; Windows executables cannot run in the container. The packaging check used the official Jellyfin portable `7.1.3-1` release as a temporary, read-only tool mount, then ran `segmentscanner doctor --config /config/worker.json` and a dry-run scan against synthetic media. This neither bundles nor pins that release for deployment.

Models are bring-your-own. `model-v1.byo.json` records an unapproved, source-unknown local model; it is not bundled, downloaded, or production-approved. The helper smoke passed against SHA-256 `9b486f3c3eee77b4c8cc91a83892c37026cca7d29b79bf3b93772ccd2db58454` with output shape `[1, 1, 80, 80]`; five correction tests passed.
